Step 0 — Choose host mode (start here)

Do this first. Before adding features or filling GUIDs, decide how the widgets will be embedded. Run init and answer the host question (or pass flags). 

npm run init
# interactive prompts: host mode → client slug → CMS platform (if needed)

# or non-interactive:
npm run init -- --host dxm --client acme
npm run init -- --host cms --client acme --cms-platform pantheon
npm run init -- --host both --client acme --cms-platform wordpress
hostMode Use when Bundle behaviour Primary docs / output
dxm Kurtosys DXM / Studio / Elementor pages IIFE, React external hosts/dxm/ · BuildResult/dxm/…
cms Client WordPress / Pantheon / custom CMS IIFE, React bundled (self-contained) hosts/cms/ · integration specs · BuildResult/cms/…
both Same widgets delivered to DXM and CMS Builds both variants from one source Both host folders · dual BuildResult trees

You do not need two monorepos. Host mode only changes packaging, deploy path, and documentation. Widget UI/source stays under development_v1/product-page-apps/.

Re-run later with npm run init -- --host cms --force (or npm run host:set) if the delivery model changes.

1. What this repo is

A generic, reusable monorepo for embeddable React product-page widgets. Each widget is a Vite app under development_v1/product-page-apps/, registered in studio.config.json.

Starter apps:

performance#performancewindow.performanceApp*5175

* window.performance is reserved by the browser; the loader uses performanceApp automatically.

4. Initialize a client project

  1. Copy the template next to the widget starter: 
    cp -R ~/Documents/GitHub/ksys-studio-pp-template ~/Documents/GitHub/acme-pp
cd ~/Documents/GitHub/acme-pp
  2. Init host mode (Step 0).
  3. If the client slug is not still client, rename folders: 
    npm run client:set -- acme
    (If you already passed --client acme to init, still run client:set when folders were created as ksys-client-*.)
  4. npm run apps:list — confirm hostMode and app folders.
  5. Fill each app’s config/env.config.cjs.

5. DXM vs CMS — how the project is factored

Shared (always)

  • One source tree per widget
  • A11y defaults, Tailwind important, security pins
  • App add / rename / client slug tooling

DXM-only factoring

  • HOST_MODE=dxm → React externalized
  • Studio GUIDs + Fundpress / applicationManager URLs
  • Outputs under BuildResult/dxm/<env>/
  • Guidance in hosts/dxm/README.md

CMS-only factoring

  • HOST_MODE=cms → React bundled (self-contained for WP/Pantheon)
  • Integration spec per product page (Confluence-style)
  • Outputs under BuildResult/cms/<env>/
  • Guidance in hosts/cms/README.md

both

npm run build:stg builds each app twice and collects into both BuildResult/dxm/… and BuildResult/cms/….

7. Develop a single app

npm run dev -- overview

Local index.html simulates App Manager + mount node for DXM-style inputs. For CMS work, the same mount data-input-* attributes are still the preferred contract.

8. Configure environments

Each app config/env.config.cjs: development / stg / prd.

  • guid, apiToken, savedSearchToken
  • filename, containerId, embedGlobalName

Do not commit production (prd) secrets to public remotes.

10. CMS integration specs

For WordPress / Pantheon (and similar), create one integration spec per product page — the same idea as your Confluence “Product Page Strategies / All Regions” templates.

  1. Copy docs/integration-specs/_TEMPLATE.md
  2. Rename to the product page (and region if needed)
  3. Fill mount selectors, script URLs, cultures, QA checklists
cp docs/integration-specs/_TEMPLATE.md \
   docs/integration-specs/acme-global-equity-us.md

See hosts/cms/README.md for embed snippets.

11. Build for dev / stg / prd

# uses studio.config.json hostMode
npm run build:dev
npm run build:stg
npm run build:prd

# force a single host even if mode is "both"
npm run build:stg:dxm
npm run build:stg:cms

Artifacts:

BuildResult/dxm/stg/overview/overview.js
BuildResult/cms/stg/overview/overview.js

Clean artifacts only. Each app build ends with clean-dist-artifacts, which deletes scaffolding (index.html, vite.svg, manifests, embed-loader, etc.) and keeps only the deployable <appId>.js (plus optional shared.css). BuildResult folders stay equally lean.

Per-app scripts also exist: build:dxm:stg, build:cms:stg, etc. Monorepo build-all sets HOST_MODE and prefers those scripts.

12. Built-in defaults

  • A11y — WCAG-oriented landmarks, contrast tokens, focus rings, jsx-a11y (see docs/ACCESSIBILITY.md)
  • Tailwind — @import "tailwindcss" important;
  • Embed global — window.<appId> (not YourAppEmbed)
  • Security pins — vite, rollup, tar, picomatch, postcss

13. Security audit reports

pip install -r tools/requirements-audit-report.txt
npm run audit:security

HTML/PDF under reports/, scoped to app packages and BuildResult bundles.

14. End-to-end checklist

  1. npm run init -- --host dxm|cms|both --client <slug>
  2. npm run client:set -- <slug> if folders still use the old slug
  3. Add/rename apps as needed
  4. Fill env.config.cjs
  5. If CMS/both: create integration specs from _TEMPLATE.md
  6. Implement UI; keep a11y patterns
  7. npm run build:stg → verify BuildResult/<host>/…
  8. Deploy (Studio upload and/or CMS CDN)
  9. npm run audit:security

15. Troubleshooting

SymptomFix
hostMode is not set on build Run npm run init first
CMS page has no React / blank widget Build with HOST_MODE=cms (React must be bundled)
DXM double-React / hook errors Use HOST_MODE=dxm (React externalized)
Styles overridden by theme / Elementor Confirm Tailwind important import in src/index.css
apps:add cannot find template Fix widgetTemplatePath in studio.config.json
